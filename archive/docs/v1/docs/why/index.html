Chapter 1: The Problem

Why Do We Need This?

The everyday habit of attaching listeners to individual elements, and the three silent traps it creates.

The Everyday Habit

Every frontend engineer learns the same first pattern in DOM scripting: find an element, attach an event listener to it. 

// The familiar instinct:
document.querySelectorAll(".delete-btn").forEach(button => {
    button.addEventListener("click", handleDelete);
});

It feels natural and intuitive. For 3 buttons on a static page, it works fine. But as applications grow into dynamic data tables, infinite lists, and interactive toolbars, this pattern silently degrades your application.

The Three Silent Traps

1. Memory Leaks

When rows or cards are removed from the DOM, their attached listeners often remain held in memory references. In long-lived single-page apps, this causes memory consumption to steadily climb.

2. Re-Render Dead Zones

When dynamic data re-renders a table or list, newly injected HTML elements do not have listeners attached. You are forced to re-run your binding routines repeatedly after every render.

3. Wiring Bloat

Hundreds of lines of code get dedicated solely to finding IDs, checking nulls, and registering callbacks. Business logic gets completely buried under repetitive DOM wiring plumbing.

The Epiphany

Instead of attaching 100 listeners to 100 elements, the browser already provides an elegant mechanism built directly into the DOM tree: Event Bubbling.

By attaching a single listener to a stable parent container, every click on current and future children naturally bubbles up to be handled in one clean, centralized place.
